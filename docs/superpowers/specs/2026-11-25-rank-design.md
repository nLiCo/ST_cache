# ③ 랭킹 / 내 정보 화면 설계

2026-11-25 작성, 2026-11-26 고침(등록 점수 추가). 새 화면 하나 + 함수 하나와 뷰 두 개를 바꾸는 마이그레이션 하나.

## 왜

SPEC "③"의 마지막 큰 화면이다. 점수로 경쟁한다는 과제의 핵심이 눈에 보이게 한다.
고친 이유(11/26): 사용자가 가장 중요하게 본 것은 **"찾기만큼 장소 등록도 활발하게"** 다. 지금 점수는 찾기만 보상해서 올릴 동기가 없다. 그래서 **등록 점수를 랭킹 점수에 합친다.** 등록 점수는 그 장소를 찾은 사람이 너무 없어도, 너무 많아도(너무 쉬워도) 낮게 한다(사용자 요청).

## 목표

- 로그인 없이 랭킹(순위·닉네임·총점·찾은 장소 수)을 본다. 총점 옆에 "찾기 / 등록" 점수 내역을 작게 보인다.
- 로그인하면 같은 화면에서 내 순위 카드, 내가 찾은 장소, 내가 올린 장소와 상태(승인 대기 / 승인 / 반려)도 본다.
- 사용자가 정했다: **내 정보는 랭킹 화면 안에 넣는다**(화면 둘로 나누지 않음).
- 사용자가 정했다: **등록 점수는 랭킹 점수에 합친다**(따로 보여 주는 안은 버림). **관리자 계정은 랭킹에서 뺀다.**

## 목표가 아닌 것

- 찾기 점수(E안) 변경.
- 랭킹 목록 자르기·검색·페이지 나누기(지인 위주라 짧다).
- 관리자 화면(안 만들기로 결정).

## 하지 말아야 할 것 (실패 조건)

- 찾기 전 장소의 이름·좌표가 새 화면 어디에서도 드러나지 않는다.
- 비로그인에게 로그인 오류나 빈 화면을 보이지 않는다.
- 쉬운 장소를 잔뜩 올린 사람이 잘 찾는 사람보다 위로 가지 않게 하는 것을 목표로 한다. 보장이 아니라, 20명이 활발할 때를 가정한 시뮬레이션에서 확인한 결과다.

## 등록 점수

**장소 하나가 올린 사람에게 주는 점수**

```
등록 점수 = 6 × min(찾은 사람 수, 5) × (1 − (찾은 사람 수 + 1) / (시도한 사람 수 + 2))
```

- 뒤의 괄호는 찾기 점수(E안)의 **난이도 보너스**(0~1)와 같은 값이다. 시도한 사람 대부분이 찾는 쉬운 장소는 작다.
- 찾은 사람이 0명이면 0점에서 시작한다(새로 올린 장소가 바로 최고점을 받지 않게).
- 찾은 사람이 늘수록 오르고, **5명부터는 더 오르지 않는다**(상수, 사용자 동의). 너무 어려워 찾은 사람이 적으면 낮다.
- **K = 6**(사용자 선택): 보통 난이도 장소 하나가 대략 11점 = 찾기 한 번(평균 13.6점) 가까이.
- 승인된 장소만 센다. 대기·반려 장소는 0점.
- **사용자 점수 = 찾기 점수 합 + 등록 점수 합.** 점수는 지금처럼 저장하지 않고 볼 때마다 계산한다. 다른 사람이 찾거나 시도하면 등록 점수도 바뀐다.
- 지인끼리 서로의 장소를 찾아 주며 등록 점수를 올리는 건 지인 규모라 막지 않는다(가짜 위치 모드를 막지 않는 것과 같은 판단).

**고른 근거 (가짜 데이터 시뮬레이션, 20명·30곳·17일, 20번 평균)**

| 수식 (K 곱하기 전, 장소 하나) | 쉬움 | 보통 | 어려움 | 너무 어려움 |
|---|---|---|---|---|
| 활동자 중 찾은 비율 r로 4r(1−r) | 0.93 | 0.82~0.65 | 0.38 | 0.17 |
| 찾은 수 × 난이도 보너스 | 2.5~2.6 | 2.3~1.8 | 1.06 | 0.42 |
| **min(찾은 수, 5) × 난이도 보너스 (채택)** | 1.6~1.8 | **1.8~1.7** | 1.06 | 0.42 |

- 앞의 두 수식은 쉬운 장소가 가장 많이 받는다. 이 정도 인원이면 쉬운 장소도 활동자의 절반을 넘게 찾지 못해서 "너무 많이 찾음" 쪽이 작동하지 않는다.
- 상한 5명은 사용자가 동의한 **상수**다. 3~5명이 적당하다는 판단(8명 이상이면 쉬운 장소가 다시 이긴다)과 아래 K=6 순위 결과는 **20명이 활발할 때**를 가정해 잰 값이다.
- 참여가 적은 지금 규모에서는 상한 5명에 거의 닿지 않아, "너무 쉬움" 감점은 주로 난이도 보너스에서 나온다. 참여가 적을 때는 쉬운 장소가 보통 장소보다 조금 더 받는다(절반 휴면 가정: 1.29 대 1.01).
- K=6일 때 쉬운 곳만 8개 올린 사람은 평균 13.4위 → 9.1위, 보통 난이도로 2~3곳 올린 사람은 평균 1계단 오른다. 1위는 그대로 찾기를 잘하는 사람이다.
- 시뮬레이션은 가정한 행동 모델의 결과다. 실제 데이터가 쌓이면 E안처럼 K와 상한을 다시 본다.

## 접근 방식

1. **등록 화면(`#upload`)과 같은 방식으로 `#rank` 화면을 하나 더 만든다. ← 선택.** 새 파일 `js/rank.js`, 화면 이름 `rank`. 기존 화면 전환 규칙(`body[data-screen]` + CSS)에 한 줄씩만 더한다.
2. 탐색 화면 안의 패널로 끼워 넣는다. 지도·격자·상세가 얽힌 전환 규칙을 건드려야 해서 버렸다.

(내 정보를 따로 둔 두 번째 화면으로 나누는 안, 등록 점수를 따로 보여 주는 안은 사용자가 거절했다.)

## 설계

**DB (새 마이그레이션 하나, 사용자가 SQL Editor에서 실행)**
- 순수 계산 함수 `upload_score(finders bigint, attempters bigint)`: 위 수식. `place_score`처럼 표를 읽지 않으므로 anon·authenticated에게 실행 권한을 준다.
- `leaderboard` 뷰 고치기
  - `score` = 찾기 점수 + 등록 점수(소수 한 자리 반올림). `rank`는 이 총점 순서.
  - **`role = 'admin'`인 사람은 줄에서 뺀다.** (Claude 판단) 관리자가 남의 장소에서 한 시도·찾기는 지금처럼 찾은 사람·시도한 사람 수에 센다. 찾기 점수(E안) 계산을 바꾸지 않기 위해서다.
  - 관리자가 올린 장소도 그대로 공개되고, 그 장소를 찾은 사람은 찾기 점수를 받는다(관리자는 랭킹에 없으므로 그 장소의 등록 점수는 아무에게도 가지 않는다).
  - 맨 뒤에 칸을 더한다: `find_score`, `upload_score`(각각 소수 한 자리), `upload_count`(승인된 올린 장소 수). `create or replace view`는 맨 뒤에 칸을 더하는 것만 허용하므로 기존 칸(`rank`, `nickname`, `score`, `found_count`, `is_me`)의 순서와 타입을 그대로 둔다.
- **(Claude 판단)** `my_places` 뷰 맨 뒤에 `finder_count`, `upload_score`를 더한다. `upload_score`는 `status = 'approved'`일 때만 계산하고 아니면 0이다(찾은 사람이 있던 장소가 나중에 반려돼도 랭킹이 세지 않는 점수를 보여 주지 않게). 내가 올린 장소마다 "3명이 찾았어요 · +9.8점"처럼 보여 주면 올릴 동기가 직접 보인다. 내 장소만 나오는 뷰라 새로 드러나는 정보는 없다.

**데이터**
- 랭킹: `leaderboard`. 비로그인 가능. 닉네임이 없는 사람과 관리자는 뷰가 거른다.
- 내 순위 카드: 위 결과에서 `is_me` 줄. 로그인했지만 닉네임이 없으면 닉네임 정하기 안내. **관리자로 로그인하면** "관리자 계정은 랭킹에 나오지 않아요".
- 내가 찾은 장소: `public_places`에서 `found`가 참인 것. `explore.js`의 `onPlacesChange`를 재사용한다.
- 내가 올린 장소: `my_places`(대기·반려 포함). 로그인했을 때만 부른다.

**화면 (모바일)**
```
 랭킹
 내 순위 3위 · 42.5점 (찾기 30.5 · 등록 12.0)      (로그인 시)
 1  민수      52.0점  찾기 52.0 · 등록 0.0   5곳
 2  지연      47.3점  찾기 35.3 · 등록 12.0  4곳
 3  한시호    42.5점  찾기 30.5 · 등록 12.0  4곳   ← 내 줄 강조
 ── 내가 찾은 장소 ──   (누르면 그 장소 상세)
 ── 내가 올린 장소 ──   돌계단 [승인] 3명이 찾았어요 · +9.8점
                         분수대 [승인 대기]
```
비로그인이면 위에 "로그인하면 내 순위가 보여요"만 더하고 랭킹 목록은 그대로 보인다.

**주소·메뉴**
- `routes.js`: `#rank` → `{ screen: "rank" }`. 순수 함수라 기존 테스트에 케이스를 더한다. `restoreHash`는 기본 화면이 아닌 주소를 되살리므로 `#rank`도 그대로 동작한다.
- `main.js`: `TAB_FOR`/`MENU_FOR`에 `rank` 추가. `rank.js`의 보이기/숨기기 함수를 `setUploadVisible`처럼 부른다.
- `index.html`: 아래 탭에 4번째 `🏆 랭킹`, PC 상단 메뉴에 "랭킹". `style.css`: `#rank` 영역(등록 화면과 같은 위치 규칙, PC에서도 지도 없이 전체 폭), 4칸 탭 폭.

**불러오는 때**
- 화면에 들어올 때마다 다시 불러온다(다른 사람이 찾으면 점수가 바뀌므로). 로그인·로그아웃으로 상태가 바뀌어도 다시 그린다.
- 실패하면 "불러오지 못했어요" 한 줄과 다시 시도 버튼. 빈 화면을 남기지 않는다.
- **배포 순서: 마이그레이션을 먼저 실행하고, 그다음 화면을 배포한다.** 지금 배포된 코드는 `leaderboard`·`my_places`를 읽지 않으므로(2026-11-26 확인) 마이그레이션을 먼저 실행해도 사이트에 영향이 없다. 순서가 바뀌어 새 칸이 없으면 랭킹 요청이 실패하고 위 실패 안내가 뜬다.
- `?mock=1`은 위치만 가짜라서 랭킹도 DB에서 그대로 불러온다.

**검증**
- Node 테스트: `parseRoute("#rank")`, 점수·순위 줄 문구 만드는 순수 함수.
- SQL: 마이그레이션 실행 후 공개 키로 실제 함수를 부른다(`POST /rest/v1/rpc/upload_score`, 권한 점검 때와 같은 방식). 기대값: (찾은 0, 시도 4) → 0, (3, 10) → 12.0, (5, 5) → 약 4.29, (8, 9) → 약 5.45(상한에 걸림).
- `leaderboard` 조회 — 관리자 없음, `score = find_score + upload_score`(반올림 오차 0.1 이내), 새 칸이 숫자로 온다.
- headless Chrome으로 비로그인 화면 확인. 로그인이 필요한 부분은 사용자가 확인한다(기존 방식).

## 점수 점검 결과 (11/25, 찾기 점수)

- `place_score`: `check_place`로만 기록하면 찾은 수 ≤ 시도 수가 성립해(`attempts`를 먼저 넣은 뒤 `finds`를 넣음) 최소값이 10보다 크고 음수·0 나눗셈이 없다. 등록 점수도 같은 괄호를 써서 0~1 범위다. SQL Editor로 직접 넣거나 지우면 깨질 수 있다.
- 실제 데이터(공개 키로 `leaderboard` 조회, 2026-11-25): 6명, 점수 95.3 / 39.2 / 27.0 / 12.5 / 12.0 / 0.0, `rank`·`score`·`found_count`는 JSON 숫자로 온다. 비로그인이라 `is_me`는 모두 false.
- 동점이면 같은 순위(`rank()`)다.

## 내 판단으로 정한 것 (사용자가 고칠 수 있음)

- 랭킹은 전체를 보여 준다. 길어지면 그때 자른다.
- 닉네임 없는 사용자는 랭킹에 안 나온다(뷰 그대로).
- 화면에 들어올 때마다 새로 불러온다(주기 갱신 없음).
- 올린 장소 상태 문구는 "승인 대기 / 승인 / 반려".
- 내가 찾은 장소와 승인된 내 장소는 누르면 사진 상세(`#place/<id>`)로 간다. 대기·반려 장소는 탐색 목록에 없어 사진·이름·상태만 보인다.
- 랭킹에서 연 상세의 ← 는 랭킹으로 돌아간다. `explore.js`의 돌아가기 판단(지금은 격자에서 열었을 때만 `history.back()`)을 "격자나 랭킹에서 열었을 때"로 넓힌다.
- `my_places`에 장소별 찾은 사람 수와 등록 점수를 더해 보여 준다.
